= Inara
:toc: macro
:toclevels: 2
:idprefix:
:idseparator: -
:source-highlighter: highlight.js

*Compile-time dependency injection for Kotlin Multiplatform — your modules are just interfaces.*

Inara turns a plain Kotlin interface into a dependency-injection module. You declare _what_ a module
offers as ordinary interface members; you decide _how_ each member is produced by supplying a
`Binding` at construction time. A KSP processor generates the implementation.

.Main.kt
[source,kotlin]
----
@DIModule
interface NetworkModule {
    val baseUrl: String
    fun httpClient(): HttpClient
    fun endpoint(path: String): String
}

// Thanks to @DIModule
val network = NetworkModule(
    baseUrl = Binding.value("https://api.example.com"),
    httpClient = Binding.single { HttpClient(baseUrl) },
    endpoint = Binding.factory { path -> "$baseUrl/$path" },
)

val endpoint = network.endpoint("users")   // "https://api.example.com/users"

@DIFactory(builds = LoginController::class, from = NetworkModule::class)
internal object LoginControllerFactory

// Thanks to @DIFactory
val loginController = LoginControllerFactory.LoginController(network)
----

No reflection. No service locator. No runtime graph. Just an interface, a generated implementation,
and a compiler that tells you when a dependency is missing.

toc::[]

== Why Inara

*Your module _is_ its own API.* A `@DIModule` interface is the contract consumers depend on.
There is no separate "component" type, no qualifier annotations, no `get<T>()` lookups. Consumers
call `module.httpClient()` — a normal method on a normal interface.

*Opinionated, by design.* No global context, no mutable context, and business code is always
independent from the DI layer — it has no notion that Inara even exists.
<<building-plain-classes,`@DIFactory`>> takes that further still, generating a class with zero
imports from Inara at all.

*Wiring is a value, not a configuration language.* A module instance is built by calling a
generated function with one `Binding` per member. Bindings are ordinary values you can pass around,
store, and swap.

*Every dependency is checked by the compiler.* Forget a binding and the builder call doesn't
compile. There is no runtime "unresolved dependency" failure mode.

*Bodies see the whole module.* A ``Binding``'s lambda runs with the module as its receiver, so any
member can reach any sibling member — including inherited ones — without you wiring anything up:

[source,kotlin]
----
Binding.single { HttpClient(this.baseUrl) }   // `baseUrl` is this module's own member
----

*`suspend` members are native.* Mark a member `suspend` and it is bound with a `SuspendBinding`,
whose every factory takes a suspending body. The generated override is itself `suspend`, so
asynchronous construction propagates the way it should instead of hiding behind `runBlocking` or a
`Deferred` you have to unwrap at every call site.

[source,kotlin]
----
suspend fun token(): Token   // bound with SuspendBinding.single { authClient.fetchToken() }
----

*Overriding is first-class.* Every module gets generated `copy(...)` overloads, so building a test
variant means overriding one member and inheriting the rest.

*Multiplatform, with no platform-specific surprises.* Inara targets every platform it supports and
behaves *exactly* the same on each of them — the sole exception is the JS/Wasm targets, where
thread synchronization is a no-op, since there is no thread to synchronize.

== Setup

Inara ships two artifacts:

[cols="1,2",options="header"]
|===
| Artifact | Purpose

| `org.kodein.di.inara:inara-runtime`
| The `Binding` types and annotations. A normal dependency.

| `org.kodein.di.inara:inara-processor`
| The KSP processor that generates implementations.
|===

=== Kotlin Multiplatform

Declare your modules in `commonMain` and run the processor once over the common metadata source set,
then feed the generated sources back into `commonMain`:

.build.gradle.kts
[source,kotlin]
----
import org.jetbrains.kotlin.gradle.tasks.KotlinCompilationTask

plugins {
    kotlin("multiplatform")
    id("com.google.devtools.ksp") // Add the KSP plugin - it hosts the Inara processor
}

kotlin {
    jvm()
    iosArm64()
    // ...your targets

    sourceSets {
        commonMain {
            // Add the KSP-generated common sources to commonMain. KSP already registers this
            // directory as an output, but IntelliJ only indexes it as source code if it is
            // also declared here explicitly.
            kotlin.srcDir(layout.buildDirectory.dir("generated/ksp/metadata/commonMain/kotlin"))
            dependencies {
                // The Inara runtime: Binding types and annotations. A normal dependency.
                implementation("org.kodein.di.inara:inara-runtime:0.1.0")
            }
        }
    }
}

dependencies {
    // Run the Inara KSP processor over the common metadata source set, once, so a single
    // set of implementations is generated for commonMain rather than one per target.
    add("kspCommonMainMetadata", "org.kodein.di.inara:inara-processor:0.1.0")
}

// Every compilation - and every per-target KSP task, which also reads commonMain as part of its
// merged source set even though it has no processor registered - consumes the KSP-generated
// commonMain sources, so all of them must wait for KSP to run.
tasks.matching { it.name != "kspCommonMainKotlinMetadata" }.configureEach {
    if (name.startsWith("ksp") || this is KotlinCompilationTask<*>) {
        dependsOn("kspCommonMainKotlinMetadata")
    }
}
----

== Core concepts

=== The module interface

Annotate an interface with `@DIModule`. Every member becomes a slot to be bound:

.AppModule.kt
[source,kotlin]
----
@DIModule
interface AppModule {
    val config: Config           // Binding<AppModule, Unit, Config>
    fun repository(): Repository // Binding<AppModule, Unit, Repository>  - same shape as above
    fun user(id: Int): User      // Binding<AppModule, Int, User>         - takes an argument
}
----

*A property and a zero-argument function are the same thing to Inara.* Both produce a
`Binding<AppModule, Unit, …>`; choosing between them is purely about how you want the call site to
read. The only thing a member's declaration decides is its _argument_ type — no parameters means
`Unit`, parameters are passed through to the binding (see <<member-shapes,Member shapes>>).

What a declaration does *not* decide is the member's lifecycle. Nothing about `val` implies a
stored constant, and nothing about `fun` implies recomputation on every call — that is entirely the
binding's job, and every choice is open to both:

.AppModule.kt
[source,kotlin]
----
AppModule(
    config = Binding.provider { loadConfig() },  // a `val`, recomputed on every read
    repository = Binding.value(FixedRepository), // a `fun`, returning a constant
    user = Binding.factory { id -> User(id) },
)
----

=== The generated builder

The processor generates a function with the same name as the interface, taking one parameter per
member:

.InaraAppModule.kt
[source,kotlin]
----
public fun AppModule(
    config: Binding<AppModule, Unit, Config>,
    repository: Binding<AppModule, Unit, Repository>,
    user: Binding<AppModule, Int, User>,
): AppModule
----

Because the parameters are named after the members, call sites read like the interface itself:

.Main.kt
[source,kotlin]
----
val app = AppModule(
    config = Binding.value(Config(debug = true)),
    repository = Binding.single { SqlRepository(config) },
    user = Binding.factory { id -> repository().findUser(id) },
)
----

=== `Binding<M, A, T>`

A binding is a recipe for producing a `T`:

.Binding.kt
[source,kotlin]
----
public interface Binding<in M, in A, out T> {
    public fun get(module: M, arg: A): T
}
----

* `M` — the module type. It is always the _leaf_ module the binding is being supplied to, which is
  what lets a body reach any sibling member through its receiver. It is _contravariant_ (`in M`): a
  `Binding<Parent, …>` satisfies a `Binding<Child, …>` slot, which is how a `composed = true` builder
  hands a parent module's own bindings straight to the child.
* `A` — the argument type: `Unit` for a property or a no-argument function, otherwise derived from
  the member's parameters (see <<member-shapes,Member shapes>>).
* `T` — the produced type.

`SuspendBinding<in M, in A, out T>` is the identical shape with a `suspend fun get`, used
automatically for `suspend` members.

== Bindings reference

All factories live on the `Binding` companion (and mirror onto `SuspendBinding`).

[cols="1,1,2",options="header"]
|===
| Factory | Signature | Behaviour

| `value(v)`
| `T`
| Always returns the same pre-built `v`. Nothing is computed.

| `provider { }`
| `M.() -> T`
| Runs the body on *every* access.

| `factory { }`
| `M.(A) -> T`
| Runs the body on every access, with the caller's argument.

| `single(safety) { }`
| `M.() -> T`
| Runs the body *once*, memoizes the result forever.

| `weakSingle(safety) { }`
| `M.() -> T`, `T : Any`
| Memoizes behind a weak reference; rebuilds after collection.

| `multiplex { }`
| `(A) -> Binding<M, Unit, T>`
| Builds and caches one sub-binding *per argument value*; never evicted, so bounded key spaces only.
|===

[source,kotlin]
----
Binding.value(Config(debug = true))
Binding.provider { System.currentTimeMillis() }
Binding.factory { id -> User(id) }
Binding.single { SqlRepository(config) }
Binding.weakSingle { ExpensiveCache() }
Binding.multiplex { key -> Binding.single { Connection(key) } }
----

=== `multiplex` — per-argument lifecycles

`multiplex` is how you give an argument-taking member a lifecycle. On its own, `factory` recomputes
every call. Wrapping a `single` in a `multiplex` gives you _one instance per distinct argument_:

[source,kotlin]
----
// One Connection per host, each built once, cached forever.
Binding.multiplex { host -> Binding.single { Connection(host) } }
----

The per-argument cache is never evicted, so `multiplex` is for a *small, bounded* key space — hosts,
tenants, an enum. Keyed on an unbounded value like a user id, a request id or a timestamp it becomes
an unbounded leak; use `factory` there. An array argument (or a generated arguments class with an
array field) never equals a fresh one, so every call misses and the cache grows per call.

=== `suspend` members

A `suspend` member gets a `SuspendBinding` automatically:

.AsyncModule.kt
[source,kotlin]
----
@DIModule
interface AsyncModule {
    suspend fun load(): Service
    suspend fun loadKeyed(key: String): Service
}

AsyncModule(
    load = SuspendBinding.single { fetchService() },
    loadKeyed = SuspendBinding.factory { key -> fetchService(key) },
)
----

`SuspendBinding` mirrors every factory above, with `suspend` bodies. Its `single` and `weakSingle`
take the same `SingleThreadSafety` mode as on `Binding`; the only difference is that `Synchronized`
guards the one-time build with a coroutine `Mutex` rather than a system lock.

== Member shapes

The member's parameters determine the binding's argument type `A`:

[cols="1,1",options="header"]
|===
| Member | Binding type

| `val name: T`
| `Binding<M, Unit, T>`

| `fun make(): T`
| `Binding<M, Unit, T>`

| `fun make(id: Int): T`
| `Binding<M, Int, T>`

| `fun make(vararg s: String): T`
| `Binding<M, Array<out String>, T>`

| `fun make(vararg i: Int): T`
| `Binding<M, IntArray, T>`

| `fun make(a: A, b: B): T`
| `Binding<M, MBindingArguments.Make, T>`

| `suspend fun …`
| the same, as `SuspendBinding`
|===

=== Multiple parameters

`Binding` carries exactly one argument. When a member takes two or more parameters, the processor
generates a `<Module>BindingArguments` container holding one `data class` per such member, named
after the member capitalized:

.Module.kt
[source,kotlin]
----
@DIModule
interface Module {
    fun va(vararg str: String): String
    fun mult(s: List<String>, i: Int): Long
    fun both(vararg ids: Int, flag: Boolean = false): String
}
----

generates

.InaraModule.kt
[source,kotlin]
----
public class ModuleBindingArguments private constructor() {
    public data class Mult(val s: List<String>, val i: Int)

    @Suppress("ArrayInDataClass")
    public data class Both(val ids: IntArray, val flag: Boolean)
}
----

and you bind against those:

.Module.kt
[source,kotlin]
----
Module(
    va = Binding.factory { parts -> parts.joinToString("-") },
    mult = Binding.factory { args -> args.s.size.toLong() + args.i },
    both = Binding.factory { args -> "${args.ids.toList()}:${args.flag}" },
)
----

== Default implementations

A member with a body in the interface gets an *optional*, nullable binding that defaults to `null`,
meaning "keep the interface's own implementation":

.DefaultsModule.kt
[source,kotlin]
----
@DIModule
interface DefaultsModule {
    val name: String
    val greeting: String get() = "Hello, $name"
    fun shout(): String = "$greeting!!!"
}
----

.DefaultsModule.kt
[source,kotlin]
----
// Defaults kept - only the abstract member must be bound.
val m = DefaultsModule(name = Binding.value("World"))
m.greeting   // "Hello, World"
m.shout()    // "Hello, World!!!"

// Any default can still be overridden.
val n = DefaultsModule(name = Binding.value("World"), greeting = Binding.provider { "Hi $name" })
n.shout()    // "Hi World!!!"  - shout()'s default body re-reads the overridden greeting
----

Default bodies are re-evaluated against the _built_ module, so a default that reads a sibling member
observes whatever that sibling was bound to.

== Copying a module

Every module gets a `copy` extension function that takes one parameter per member, each defaulting to
the binding the module _currently_ holds for that member, so you override exactly what you name:

.Main.kt
[source,kotlin]
----
val testModule = appModule.copy(
    repository = Binding.value(FakeRepository()),
)
----

An omitted parameter carries the original binding across untouched — including a `single` /
`weakSingle` / `multiplex` binding's memoised state, and, for a member with a default implementation,
its _unbound_ state (that default body then re-runs against the _new_ module, so it still observes
siblings you overrode in the same `copy` call). A member with a default implementation additionally
accepts an explicit `null`, which forces it back to the interface's own body.

== Inheritance and composition

=== `@DIModule` inheritance — flattening

A `@DIModule` interface may extend other `@DIModule` interfaces. Inherited members are bound exactly
as if declared directly on the child:

.AppModule.kt
[source,kotlin]
----
@DIModule interface GreeterModule { val greeting: String }
@DIModule interface CounterModule { fun next(): Int }

@DIModule
interface AppModule : GreeterModule, CounterModule {
    val label: String
}

AppModule(
    greeting = Binding.value("Hi"),   // inherited
    next = Binding.provider { 0 },    // inherited
    label = Binding.value("app"),     // own
)
----

Every binding is parameterized on the leaf module (`Binding<AppModule, …>`), so an inherited member's
body can reach members declared on the child.

Diamond inheritance is allowed here: a shared ancestor reached through two paths contributes its
members exactly once.

=== `composed = true` — building from parent modules

When you want to build a module from _already-built_ parent modules rather than rebinding their
members, pass `composed = true` to `@DIModule`. It adds a second builder overload:

.AppModule.kt
[source,kotlin]
----
@DIModule(composed = true)
interface AppModule : GreeterModule, CounterModule {
    val label: String
}
----

You now get *two* builders:

.Main.kt
[source,kotlin]
----
// 1. From parents: pass built parent modules, bind only the child's own members.
val app = AppModule(
    greeterModule = greeter,        // an existing GreeterModule instance
    counterModule = counter,        // an existing CounterModule instance
    label = Binding.value("app"),
)

// 2. Full: bind every member individually (identical to plain @DIModule).
val app2 = AppModule(
    greeting = Binding.value("Hi"),
    next = Binding.provider { 0 },
    label = Binding.value("app"),
)
----

…and an extra `copy` overload that swaps out a whole parent at once:

[source,kotlin]
----
val withOtherGreeter = app.copy(greeterModule = differentGreeter)
----

Parent parameter names are derived from the parent's name, decapitalized (`GreeterModule` →
`greeterModule`).

Both overloads build the same implementation. When a parent is an Inara-generated module — from any
Gradle module — each of its members' bindings is carried across *as-is*: a `single` keeps its
memoised instance through a `copy`, for example. A parent that's hand-written (or an inherited member
taking two or more parameters) is read through a lightweight delegate instead.

*Diamond inheritance is rejected for `composed = true`.* Two parents both supplying the same
ancestor's members is ambiguous — which instance would the child read that member from? — and the
generator does not attempt to disambiguate it. Plain `@DIModule` has no such constraint.

== Extending non-module interfaces

A `@DIModule` interface may extend *any* interface, not just annotated ones. Members reachable
through a plain supertype are bound exactly like the module's own:

.TaggableModule.kt
[source,kotlin]
----
interface Taggable {
    val id: String
    fun tag(): String = "tag:$id"
}

@DIModule
interface TaggableModule : Taggable {
    val extra: Int
}

TaggableModule(
    id = Binding.value("x1"),   // from Taggable - abstract, so required
    extra = Binding.value(7),
    // `tag` is also from Taggable, but it has a default body, so its binding is optional
)
----

Generic supertypes work too — type arguments are substituted:

.StringConverterModule.kt
[source,kotlin]
----
interface Converter<T> {
    val default: T
    fun convert(input: T): T
}

@DIModule
interface StringConverterModule : Converter<String> { val prefix: String }

// convert is bound as Binding<StringConverterModule, String, String>
----

A plain supertype's members can't be sourced from a parent module: under `@DIModule(composed = true)`
they appear as binding parameters on the from-parents builder, alongside the module's own
declarations.

== Ignored members

Three member shapes cannot be represented by a `Binding` at all — it has no setter, no extension
receiver, and its type arguments are fixed per instance:

* `var` properties
* extension members
* generic functions

If such a member *has a default implementation*, it is silently excluded from the module's bindable
surface: no `Binding` parameter, no override in the generated class. Ordinary Kotlin inheritance
resolves it to the interface's own body.

.Module.kt
[source,kotlin]
----
@DIModule
interface Module {
    val name: String                                  // bound normally

    var tag: String                                   // ignored: both accessors defaulted
        get() = "default-tag"
        set(_) {}

    val String.shoutedLength: Int                     // ignored: extension with a body
        get() = uppercase().length

    fun <T> identity(value: T): T = value              // ignored: generic with a body
}

val m = Module(name = Binding.value("x"))   // only `name` is a parameter
m.tag                                        // "default-tag"
m.identity(42)                               // 42
----

Without a default implementation these are *compile errors* — there would be no way to satisfy
them. A `var` needs _both_ accessors implemented to qualify; one abstract accessor still leaves
something unsatisfiable.

== Visibility and nesting

An `internal` module interface gets an `internal` implementation class, builder, `copy`
functions, and arguments container:

.InternalModule.kt
[source,kotlin]
----
@DIModule
internal interface InternalModule { val secret: String }
----

A module interface must be `public` or `internal`. A `private` or `protected` one is a compile
error — the generated top-level builder and `copy` functions could not name it.

A nested module interface is supported. The generated implementation class, file and `copy`
functions flatten the enclosing scopes (`InaraOuterInner`), but the builder function keeps the
interface's own simple name (`Inner`), so you call it the way you'd write the interface. Two
same-simple-named nested modules in one package therefore share a builder name — harmless once
either has a member (their `Binding` parameter types differ, so the functions are valid overloads),
and a compile error flagged on the generated files in the rare case that both are member-less:

.Outer.kt
[source,kotlin]
----
interface Outer {
    @DIModule
    interface Inner { val label: String }
}

val inner: Outer.Inner = Inner(label = Binding.value("inner"))
// generated: public class InaraOuterInner(...) : Outer.Inner
----

== Building plain classes

Everything so far builds a `@DIModule` interface itself. `@DIFactory` builds something else with it:
a plain constructor-shaped function for a class that never references Inara at all. Annotate a
`public` or `internal` object with `builds`/`from`, and the processor generates - per `@DIFactory`
annotation, it is repeatable (see <<multiple-factories-from-one-object>>) - an extension function on
that object, named after `builds`, that resolves every constructor argument off a module instance:

.UsersController.kt
[source,kotlin]
----
class UsersController(val httpClient: HttpClient, val endpoint: String)

@DIFactory(builds = UsersController::class, from = NetworkModule::class)
public object UserControllerFactory {
    internal fun NetworkModule.argEndpoint(): String = endpoint("users")
}
----

generates

.InaraUserControllerFactory.kt
[source,kotlin]
----
public fun UserControllerFactory.UsersController(module: NetworkModule): UsersController =
    UsersController(
        httpClient = module.httpClient(),
        endpoint = module.argEndpoint(),
    )
----

`UsersController` itself has no idea Inara exists — call the generated function off the object:

[source,kotlin]
----
val controller = UserControllerFactory.UsersController(network)   // `network` is a built NetworkModule
----

The generated function has the same visibility as the annotated object, and its own `arg<Argument>`
functions are visible because the object is the extension receiver. Marking the object `public` when
its `from` module, `builds` class, selected constructor, `with` / `withNullable` type, or any
pass-through parameter's type (see <<pass-through-arguments,Pass-through arguments>>) is `internal`
is a compile error — that signature couldn't compile — so make the object `internal` in that case,
or the type `public`. On a `public` object every `arg<Argument>` function must be `internal`: they
are implementation detail, not public API. A pass-through parameter whose type is `internal` in a
_different_ module is always a compile error, regardless of the object's own visibility — such a
type could never be named from generated code at all.

=== Resolving constructor arguments

Each constructor argument is resolved independently, in priority order:

. An `arg<Argument>` extension function declared on the annotated object — `fun
  NetworkModule.argEndpoint(): String` resolves an argument named `endpoint`. This is the _only_
  thing a `@DIFactory` object may declare; anything else is a compile error. The generated function
  is an extension on the object, not a member, so a `private` one is unreachable and a compile error;
  on a `public` object it must be `internal`. When the object carries several `@DIFactory`
  annotations the function serves each one whose `from` and selected constructor match it (see
  <<multiple-factories-from-one-object>>).
. Otherwise, under `with` / `withNullable` (see below), the call-time value itself, when its type is
  assignable to the argument. The caller supplied it for this very call, so it outranks both the
  argument's own default and any `from` member — it shadows a same-typed member rather than tying
  with it. A `vararg` is never resolved this way.
. Otherwise, if the parameter can be omitted from the call — it declares a default value, or is a
  `vararg` — it is left out, and Kotlin applies the default (an empty array for a `vararg`). A
  default written on the `builds` class thus outranks any `from` member: it is a deliberate local
  statement of intent, a type match is not. A parameter that already has a default needs no
  `arg<Argument>` function to restate it.
. Otherwise,
.. A uniquely-typed member of `from` — `httpClient` above resolves automatically because
   `NetworkModule.httpClient()` is the only member returning `HttpClient`, exactly. A member that
   takes one argument is a candidate only under `with` / `withNullable` (see below); every other member
   must take none.
.. Failing an exact match, a uniquely-typed _assignable_ (supertype) member.
. Otherwise, the argument becomes a parameter of the generated function itself — see
  <<pass-through-arguments,Pass-through arguments>>.

Two or more matching `from` members (step 4) is always a compile error, never something silently
deferred to the caller — that's a real mistake in the module, distinct from step 5's "nothing at all
matched".

Because `arg<Argument>` is a reserved naming convention, a `@DIModule` member itself may not be named
`arg` followed by an uppercase letter.

=== `with` — a call-time argument

Some values aren't knowable at module level — a request context, a screen route, the id of the user
this instance is for. `with` gives the generated function a second parameter for one:

.UserSession.kt
[source,kotlin]
----
class UserSession(val httpClient: HttpClient, val greeting: String)

data class RequestContext(val userId: String)

@DIFactory(builds = UserSession::class, from = NetworkModule::class, with = RequestContext::class)
public object UserSessionFactory {
    internal fun NetworkModule.argGreeting(context: RequestContext): String = "Hello, ${context.userId}"
}
----

.InaraUserSessionFactory.kt
[source,kotlin]
----
public fun UserSessionFactory.UserSession(module: NetworkModule, with: RequestContext): UserSession =
    UserSession(
        httpClient = module.httpClient(),      // resolved as usual, no `with`
        greeting = module.argGreeting(with),   // the call-time value flows in
    )
----

When `with` is set (it defaults to `Unit` — no parameter, everything above unchanged):

* A constructor argument whose type the `with` value is assignable to resolves straight to it, ahead
  of that argument's default and any `from` member (see step 2 of
  <<resolving-constructor-arguments,Resolving constructor arguments>>) — shadowing a same-typed
  member rather than needing a trivial `arg` function that just returns it. A `vararg` argument is
  never resolved this way.
* Every `arg<Argument>` function must take exactly one parameter of the `with` type — no parameter,
  or another type, is a compile error.
* A member of `from` taking a single parameter the `with` value fits into — or a `vararg` whose array
  type it is — joins the automatic-resolution candidate pool, on equal footing with a zero-parameter
  member. A zero- and a one-parameter member matching the same argument is an ambiguity error, just
  as two zero-parameter members are.

Use `withNullable` instead of `with` for a nullable parameter — `fun
UserSessionFactory.UserSession(module: NetworkModule, with: RequestContext?)`. It is `with` in
every other respect, except that every
`arg<Argument>` function must then declare its parameter as `RequestContext?`, only a `from` member
whose single parameter accepts `null` is an automatic-resolution candidate (a `vararg` never is), and
setting both `with` and `withNullable` is a compile error.

[#pass-through-arguments]
=== Pass-through arguments

`with` carries exactly one call-time value, shared by every argument its type fits. Step 5 of
<<resolving-constructor-arguments,Resolving constructor arguments>> covers the rest: a constructor
argument nothing above resolves simply becomes a parameter of the generated function - named
`arg<Argument>` (exactly the naming convention an `arg<Argument>` function already uses) and typed
after the constructor parameter - and passed straight through:

.Ticket.kt
[source,kotlin]
----
class Ticket(val httpClient: HttpClient, val subject: String, val priority: Int)

@DIFactory(builds = Ticket::class, from = NetworkModule::class)
internal object TicketDIFactory
----

.InaraTicketDIFactory.kt
[source,kotlin]
----
internal fun TicketDIFactory.Ticket(module: NetworkModule, argSubject: String, argPriority: Int): Ticket =
    Ticket(
        httpClient = module.httpClient(),   // resolved as usual
        subject = argSubject,               // pass-through: nothing in NetworkModule provides a String
        priority = argPriority,             // or an Int
    )
----

A generated signature is legible by prefix alone: one `module` argument, zero or one `with` argument,
and zero or more `arg*` arguments — and the `arg` prefix makes a pass-through parameter's name never
collide with the literal `module` or `with`. Pass-through parameters come after `module` and (if set)
`with`, in `builds`'s constructor declaration order — interleaved with resolved arguments in that same
order determines only the constructor call, not the generated function's own parameter list. A
`vararg` parameter is never one of them: it's always omissible (step 3), so it never reaches step 5.
Neither is a parameter with two or more matching `from` members — that's an ambiguity error (step 4),
not something deferred to the caller. Two sibling pass-through parameters that would otherwise land on
the same `arg<Argument>` name (e.g. constructor parameters `count` and `Count`) are disambiguated with
a trailing `_`.

Two things follow directly from this: a constructor parameter's type has to be nameable from the
generated function, exactly like `from`, `builds` and `with` (see above) — a `public` `@DIFactory`
object with an unresolvable `internal`-typed argument is a compile error, and a type `internal` in a
_different_ module can never pass through at any visibility. And because a default (step 3) still
outranks a pass-through (step 5), adding a default to a constructor parameter that used to be a
pass-through parameter silently removes it from the generated function's signature — a source
change for every caller, with no diagnostic warning you about it.

=== `suspend` arguments

By default (`Suspend.Allow`), a `suspend` provider — an `arg` function or a `suspend` module member —
is just as eligible as a non-`suspend` one, and the generated function itself becomes `suspend` if
and only if an argument actually resolved to one:

.AsyncGreeter.kt
[source,kotlin]
----
class AsyncGreeter(val service: Service)

@DIFactory(builds = AsyncGreeter::class, from = AsyncModule::class)
public object AsyncGreeterFactory
----

.InaraAsyncGreeterFactory.kt
[source,kotlin]
----
// generated:
public suspend fun AsyncGreeterFactory.AsyncGreeter(module: AsyncModule): AsyncGreeter =
    AsyncGreeter(
        service = module.load(),   // AsyncModule.load() is a suspend member
    )
----

`suspend = Suspend.Forbid` excludes every `suspend` candidate from resolution entirely — rather than
being silently skipped, a `suspend`-only argument simply falls through to a pass-through parameter
(see <<pass-through-arguments,Pass-through arguments>>), like any other argument nothing else
resolves — and the generated function is never `suspend`. `suspend = Suspend.Force` resolves exactly
like `Allow` but always generates a `suspend` function, whether or not any provider actually is.

=== `constructorIndex` — building through a non-primary constructor

By default `@DIFactory` calls ``builds``'s primary constructor. `constructorIndex` selects a different
one instead, in declaration order (`0` the primary, `1` the first secondary, `2` the second, …) —
useful when the intended entry point isn't the primary constructor, e.g. a `private` primary paired
with a public secondary:

.Greeter.kt
[source,kotlin]
----
class Greeter private constructor(val greeting: String, private val marker: Int) {
    constructor(baseUrl: String) : this("Hello from $baseUrl", 0)
}

@DIFactory(builds = Greeter::class, from = NetworkModule::class, constructorIndex = 1)
public object GreeterFactory
// generated: public fun GreeterFactory.Greeter(module: NetworkModule): Greeter =
//                Greeter(baseUrl = module.baseUrl)
----

Only the selected constructor's parameters are resolved — every other constructor, including the
primary, is ignored entirely, `arg<Argument>` name-matching included.

[#multiple-factories-from-one-object]
=== Multiple factories from one object

`@DIFactory` is repeatable. Annotate one object several times to build several related classes; each
annotation generates its own function, all in one file named after the object:

.Screens.kt
[source,kotlin]
----
class LoginScreen(val heading: String)
class HomeScreen(val heading: String, val count: Int)

@DIFactory(builds = LoginScreen::class, from = ScreenModule::class)
@DIFactory(builds = HomeScreen::class, from = ScreenModule::class)
public object ScreensFactory {
    internal fun ScreenModule.argHeading(): String = "…"
}

// generated, in InaraScreensFactory.kt:
//   public fun ScreensFactory.LoginScreen(module: ScreenModule): LoginScreen = …
//   public fun ScreensFactory.HomeScreen(module: ScreenModule): HomeScreen = …
----

An `arg<Argument>` function is shared: it serves every `@DIFactory` whose `from` is its receiver and
whose selected constructor has a matching parameter — above, `argHeading` fills `heading` for both
screens. A declared `arg` function that fits none of the annotations is a compile error. `with`,
`suspend` and `constructorIndex` are per-annotation, so one object can generate a `suspend` function
next to a plain one. Two annotations that would generate the same signature — same `builds`, `from`,
`with` type, and pass-through parameter types (see <<pass-through-arguments,Pass-through
arguments>>) — are a compile error; `constructorIndex` can now tell two otherwise-identical
annotations apart, if the constructors it selects leave different arguments unresolved.

== Thread safety

`Binding.single` / `Binding.weakSingle` (and their `SuspendBinding` counterparts) take a
`SingleThreadSafety` mode:

[cols="1,2",options="header"]
|===
| Mode | Guarantee

| `Synchronized` (default)
| The builder runs *exactly once*, under a lock.

| `Published`
| Lock-free. Concurrent callers may each run the builder, but all callers converge on a single winning instance.
|===

[source,kotlin]
----
Binding.single(SingleThreadSafety.Published) { ExpensiveButPureValue() }
----

`multiplex` keeps its per-argument cache as a lock-free copy-on-write map: an already-cached
argument is a plain atomic read with no contention, and two *first-time* arguments briefly race to
extend the cache (the loser retries, the caller's builder still runs at most once). Filling the
cache with n distinct arguments is O(n²) — acceptable, and intended, only for the *small, bounded*
key space `multiplex` is meant for.

`weakSingle` holds its value behind a platform weak reference and rebuilds on the next access
after collection.

`SuspendBinding.single` / `weakSingle` take the same `SingleThreadSafety` mode as `Binding`;
`Synchronized` guards the one-time build with a coroutine `Mutex` instead of a system lock.

== Supported platforms

`inara-runtime` is a Kotlin Multiplatform library targeting:

* *JVM*
* *iOS* — `iosArm64`, `iosSimulatorArm64`, `iosX64`
* *watchOS* — `watchosArm32`, `watchosArm64`, `watchosDeviceArm64`, `watchosSimulatorArm64`
* *tvOS* — `tvosArm64`, `tvosSimulatorArm64`
* *macOS* — `macosArm64`
* *Android Native* — `androidNativeArm32`, `androidNativeArm64`, `androidNativeX64`, `androidNativeX86`
* *Linux* — `linuxX64`, `linuxArm64`
* *Windows* — `mingwX64`
* *JS* — browser, Node.js
* *Wasm/JS* — browser, Node.js

`macosX64` (Intel macOS) is deliberately not a target: Kotlin deprecated it in 2.3.20 and will
remove it. `iosX64` — the Intel iOS _simulator_, not Intel hardware — is kept because it is still a
supported target.
